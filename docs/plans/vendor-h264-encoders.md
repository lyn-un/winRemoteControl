## 一、背景与问题边界

实施前 `KWebRtcH264Encoder::SetRates()` 把 WebRTC 目标传入 `KH264Encoder`。x264 路径通过平均码率、最大码率和 VBV 参数重配置；旧 MF 路径依赖项目对 `libavcodec/mfenc.c` 的补丁调用 `ICodecAPI::SetValue()`。新构建已撤销该 MF 补丁，MF 仅保留初始化码率。

已知证据：

- x264 动态码率实际编码回归已通过，用户反馈窗口切换模糊明显减轻，但尚有轻微现象。
- Intel MF 日志中运行时设置返回 `S_FALSE`。补丁目前仅判断 `FAILED(hr)`，错误地记录为已接受；按接口定义，`S_FALSE` 表示属性只读。
- AMD MF 实测返回成功且输出有响应，但动态 6 Mbps 阶段约 18 Mbps，与固定 6 Mbps 对照偏差过大，硬件验收未通过。
- 两个 MF 问题不同，不能都归为“设置接口失败”，也不能据此认定硬件本身存在缺陷。

本方案目标是建立可验证的厂商编码路径，不预先承诺彻底解决场景切换模糊或降低端到端延迟。GPU/驱动能力决定后端可用性，不能仅依据 CPU 品牌选择编码器。

## 三、阶段 A：构建一次包含三个后端的 FFmpeg

### 3.1 源码与工具链

沿用现有 FFmpeg 基线 `239f2c733d`、x264 `c24e06c2e184345ceb33eb20a15d1024d9fd3497`、便携 NASM 2.16.03 和现有 MSYS2 UCRT64 工具链。先核对该提交的 `configure` 与后端源码，不默认套用最新文档选项。

| 后端 | 构建依赖方向 | 运行依赖与注意事项 |
| --- | --- | --- |
| QSV | oneVPL dispatcher/开发文件；核对该基线 `--enable-libvpl` 支持 | 可用 Intel GPU 与驱动实现；若动态链接 dispatcher，部署允许分发的匹配 DLL |
| AMF | AMD AMF 开发头文件，启用 AMF | AMD 驱动提供的 AMF 运行时；不能把构建头文件当作运行时 |
| NVENC | `nv-codec-headers`/`ffnvcodec`，启用 NVENC | 支持所选 SDK API 版本的 NVIDIA 驱动；仅编码不应无理由引入整套 CUDA Toolkit |

新增依赖已通过 `tools/ffmpeg/vendor-dependencies.json` 锁定准确版本、下载地址和 SHA-256，不使用浮动 `latest`。选择依据和最低驱动要求见厂商构建文档。若 oneVPL 不覆盖目标 Intel 代际，先报告兼容性缺口，不静默换成另一套 dispatcher。

新增工具缺失时列出清单，不自动安装系统软件、不升级显卡驱动、不改全局 PATH。构建检查无需本机同时拥有三家显卡。

### 3.2 输出与缓存

- 新依赖安装到独立目录，例如 `third_party/ffmpeg-wrc-vendor`；中间产物放入忽略的 `build/ffmpeg-vendor`。
- 原发行包和现有 MF original/patched 对照目录可保留为历史实验归档，但新构建不得从 patched 目录复制源码或 DLL。
- 从校验通过的上游归档重新解压到新源码目录，不对旧实验源码做不确定的反向打补丁；确认 `mfenc.c` 与固定上游版本一致。
- 在现有 `tools/ffmpeg/` 脚本基础上增加明确构建配置；头文件、导入库、DLL 必须来自同一输出目录。
- 构建配置显式启用五个 H.264 编码器及所需硬件设备支持，保留当前 H.264 解码、解析、像素转换和项目链接依赖。`--disable-everything`/`--disable-autodetect` 下逐项核对，不能只增加编码器名字。
- 缓存按源码、依赖、配置和实际补丁集内容哈希失效；新配置不应用 `mf-dynamic-bitrate.patch`，不得复用旧 `.wrc-patched` 标记或 MF 补丁版编译产物。
- 保留最小化构建；无需为了查询编码器而部署完整 FFmpeg CLI，可提供链接同一库的只读能力探针。
- 记录 FFmpeg 版本后缀、配置、依赖版本、补丁摘要、运行时文件及哈希。部署所有必要 dispatcher/工具链 DLL，并核对许可证和对应源码提供要求；不复制显卡驱动 DLL。

### 3.3 构建验收

1. `avcodec_find_encoder_by_name()` 能找到 QSV、AMF、NVENC、x264、MF；此项只证明编入。
2. 在无某厂商 GPU 的机器仍能启动程序、使用 x264；缺少可选硬件不可导致进程装载失败。
3. 在无开发环境 PATH 的普通运行环境检查 DLL 依赖闭包。
4. 完整重建应用，使用 `FFMPEG_ROOT` 切换，只部署 `build/Release`；不得混用旧 DLL。
5. 发布包不得夹带本机 `security`、可信设备记录、日志或个人设置。跨机更新程序应保留目标机器自身身份数据。
6. 核对新安装目录与 `build/Release` DLL 哈希及构建标识一致，明确不含旧 MF 动态补丁；删除补丁文件本身不算完成运行时回退。

## 四、阶段 B：QSV 与 AMF 应用接入

### 4.1 保持接口，隔离后端差异

继续使用 `KWebRtcH264Encoder → KH264Encoder → avcodec`。沿用现有职责，不建立新通用插件框架；后端选项和更新能力用小型配置/辅助函数表达。

- 扩展 `KVideoEncoderPreference` 和现有 `--diagnostic-video-encoder` 解析，计划支持 `h264_qsv`、`h264_amf`。
- `h264_nvenc` 暂不作为可用应用选项，帮助文字明确“库已包含，应用未接入”，不得伪装已支持。
- 首轮 `auto` 保持现有行为；强制选择 QSV/AMF 不静默回退 x264，以免硬件测试实际跑了软件。
- 初始化探测区分编入、驱动存在、设备可用、配置可打开、动态码率通过五个层级；日志记录实际 GPU/适配器及选择原因。
- 多 GPU 时明确选择与采集适配器的关系。不能在某卡失败后悄悄换卡，却继续记录原设备。

### 4.2 帧格式、输出和线程

- 第一版允许继续由现有 I420 转 NV12，不将 GPU 零拷贝纳入验收。
- QSV 若要求硬件帧，建立明确的设备/帧上下文和上传路径；AMF 同样按真实支持的输入格式配置。拒绝不支持的格式，不假设各后端接受相同 AVFrame。
- 处理输入 stride、padding、支持的尺寸/对齐约束及资源寿命；保持现有画面布局与坐标映射。
- 正确处理 `EAGAIN`、延迟出包和最终 drain，不能假设每次送入一帧立即得到对应的一包。
- 按输出 PTS 找回输入 RTP 时间戳、采集时间及帧元数据；必要时增加有界待输出映射，不把旧输出套上当前输入时间戳。断开、失败、重建时清理并隔离迟到输出。
- 编码与参数更新沿用串行编码线程语义；设备上下文与帧资源使用明确所有权。
- 保持现有 H.264 协商兼容性，核对实际 SPS profile/level、Annex B、SPS/PPS、IDR；不直接照抄 Sunshine High Profile 设置造成与 SDP 不一致。

### 4.3 低延迟与动态码率

以无 B 帧、浅异步队列为起点；码率模式、VBV 和后端选项必须逐个检查设置/打开结果。Sunshine 参数仅为参考，不整体照搬，尤其不可复制其 GOP 策略。

| 后端 | 实施前必须核对 | 验收重点 |
| --- | --- | --- |
| QSV | 本基线 `qsvenc.c` 的 `update_bitrate`/reset 路径与可变参数、单位及取整 | 目标修改触发实际重配置；确认 reset 是否引入关键帧或序列变化 |
| AMF | 本基线 `amfenc*` 是否消费运行时变化，目标/峰值/VBV 是否更新 | 不能因为原生 AMF 支持动态属性就认为 FFmpeg 已接通 |
| NVENC | 只记录本基线动态重配置能力与后续注意事项 | 本阶段不宣称硬件可用或动态码率通过 |

- 若 AMF 基线没有需要的动态更新，暂停该后端验收，优先评估包含所需实现的上游版本。任何新增第三方补丁或源码基线升级都单独说明并确认，不在撤销 MF 补丁的同时隐式增加另一份补丁；不能悄悄重建编码器冒充动态更新。
- 继续由 WebRTC 提供目标；相同值不重复提交，非正值保留现有处理语义，范围与单位转换使用宽整数并检查。
- 区分平均目标与峰值，核对初始化帧率、输入 PTS、真实送帧节奏，不能凭三倍偏差硬编码补偿。
- 不因每次 `SetRates` 主动重开编码器或请求关键帧；若后端自身会产生 IDR，测量并明确报告。
- 初始化失败明确原因；运行时重配置失败沿用编码错误/会话处理，不静默继续声称采用新目标，不新增运行时跨后端自动切换。
- 先不实现码率过滤、降档等待等策略，避免其掩盖后端重配置缺陷。

## 五、诊断与测试

### 5.1 诊断

沿用现有 session/latency 追踪，记录请求后端、实际后端、FFmpeg 构建标识、GPU/驱动、初始化选项和回退原因。新增信息使用明确命名：

- `requestedBitrateBps`：WebRTC 请求。
- `reconfigureResult`：已执行、无变化、不支持或失败；没有公开证据时不能声称底层 API 已接受。
- `measuredBitrateBps`：按完整编码输出字节及媒体时间窗口计算，不外推稀疏采样帧。
- 编码耗时、输入/输出帧数、关键帧、丢弃及队列水位。

统计按秒汇总或异步采样，不逐帧同步落盘。保留 `--latency-trace` 强制 BGRA 的当前语义；编码端对比不得顺带宣称验证了 GPU 显示端到端收益。

### 5.2 自动化测试

- 纯逻辑：后端选择、显式请求不回退、参数映射、重复/零/负值/溢出、200 次调整不重建和不主动请求关键帧、错误传播。

### 5.3 显式硬件验收

QSV、AMF 分别显式启用。无目标硬件/驱动时明确跳过；有硬件但配置、编码或重配置失败时记失败，不能转为跳过或用 x264 顶替。

复用统一可重复动画：1280×720、30 FPS、固定随机种子；同一编码实例 1→6→1 Mbps，每阶段 300 帧，舍弃前 60 帧，同时运行固定 1 Mbps 和固定 6 Mbps 的同内容对照。

验收要求：

- 高阶段输出至少为前低阶段两倍，恢复低阶段不超过高阶段 60%。
- 动态稳定段与对应固定对照偏差不超过 30%；同时报告与请求目标的偏差，即使相对对照通过也不能隐藏两者都偏离目标的问题。
- 高阶段亮度 PSNR 不低于对应低阶段；按相同源帧比较。
- 按输出 PTS 连续解码，检查完整帧数和尺寸；阶段切换不排空，不通过重建满足码率测试。
- 报告关键帧变化和编码器重建计数；未达标不降低阈值。
- 补充 1080p/60 FPS 性能观察及重复启动释放检查，记录 CPU、编码耗时和资源变化，不预设收益。

NVENC 的“可枚举”仅为构建检查。其实际编码、动态码率和资源验收列为后续未完成项，即使开发机有 NVIDIA 显卡也不能混淆两者。

## 七、暂缓问题：接收端高 DPI 缩放与画面模糊（2026-10-11）

- 状态：已记录，待验证、待修复。用户最新要求将本项和 HDR 一并暂缓，优先完成厂商编码器接入与验收。
- 场景：AMD 被控端显示器为 27 英寸、2560×1440；Intel 控制端为 14 英寸、1920×1080。关闭 HDR 后明显流畅，但 AMF 和 libx264 均被反馈画面仍模糊。
- 已有证据：libx264 对照日志确认编码和接收解码尺寸均为 2560×1440，最后接收统计的累计丢包和解码丢帧均为 0。日志位于两端运行目录的 `logs/x264-hdr-off`，不纳入版本控制。
- 静态线索：`src/render/videorenderwidget.cpp` 的 `initializeD3d()`、`resizeEvent()` 和 `render()` 直接使用 Qt `size()` 配置交换链缓冲区和 D3D 视口，未显式换算物理像素。高 DPI 下可能先缩到逻辑尺寸，再放大到窗口物理尺寸，形成额外模糊。
- 尚未确认：Intel 的 Windows 缩放比例、实际窗口客户区物理尺寸与交换链尺寸；不能把上述线索直接当作已复现根因，也不能认定全部模糊都由缩放造成。1440p 缩小到 1080p 本身也会损失细节。
- 后续验证：记录窗口逻辑尺寸、DPI/设备像素比、客户区物理尺寸、交换链/视口尺寸及视频显示矩形；对照 100%/125%/150% DPI、窗口/全屏及可用的 1:1 像素显示；用静止文字和细线图案区分正常缩小、额外缩放和压缩失真。
- 后续修复边界：若确认尺寸不匹配，使用正确的物理尺寸创建/调整渲染目标，同时保持 Qt 布局和输入坐标映射一致；验证跨屏 DPI 变化和点击位置，不顺带修改编码器或协议。

## 八、暂缓问题：HDR 采集性能与 SDR 转换质量（2026-10-11）

- 状态：用户明确要求先记录、停止本轮优化，回到厂商编码器主线。未实现查表、GPU 转色或新色调映射方案。
- 现象：AMD 被控端开启 HDR 时采集明显低帧率，关闭后流畅度显著改善；开关对照和 WPR 数据保留在本机忽略的 `performance-baseline.md` 及 `build/hdr-profile`。
- 性能证据：WPR CPU 采样经本机系统符号解析确认 `ucrtbase.dll!powf` 是远控进程最大已识别热点。自有代码显式幂运算位于 `src/capture/dxgidesktopduplicator.cpp` 的 `LinearToSrgb()`，HDR FP16 路径对每像素三个通道分别调用。尚无匹配的主程序 PDB 将全部调用栈映射到源码，不把全部采集墙钟耗时等同于 powf 时间。
- 当前处理：DXGI FP16 纹理读回 CPU；半精度转 float；除以固定 `m_fSdrWhiteScale=2.5f`；裁剪到0～1；按 sRGB 曲线转换并量化到8位 BGRA，再进入 I420/H.264 SDR 链路。
- 质量限制：sRGB 曲线是标准公式，但固定白电平加裁剪不是完整、已验证的 HDR→SDR 色调映射；可能丢失高光，不能称为等价 SDR。当前未动态读取 Windows SDR 白电平。
- 后续范围：先比较成熟的实时 HDR→SDR 实现与 D3D11 接入成本，再选择优化路径；分别验证颜色/高光、白电平、CPU/GPU耗时及资源生命周期。若仅优化性能，应与原转换输出对照，不隐式改变色彩策略。
- 本轮验收可在明确记录 HDR 关闭的条件下继续；HDR 开启性能及 HDR 画质仍列为已知限制，不因此自动放宽 AMF 码率门槛或宣布整体画质通过。
